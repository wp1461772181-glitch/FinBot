# owner 与 Claude 的协作规范

> 状态：2026-11-26 起草，经仓库根 `CLAUDE.md` 引用生效。owner 当天裁定了「测试怎么跑」「谁来验收」两处；其余条目 owner 可随时改。
> 来源：2026-11-21 至 11-26 owner 的历次反馈和黑豹事故。每条后面括号里是出处日期。
> 产品设计的三条核心准则在仓库根 `CLAUDE.md`，本文件只管「怎么一起干活」。

## 一、够不着的机器（黑豹）

黑豹没有 HDMI、没接串口，唯一的现场通道是 owner 手里的 TF 救援卡。出了事，代价是 owner 本人到现场动手。（11-25 事故）

1. 任何可能让它起不来或断网的改动，动手前先确认有退路。这类改动包括：启动参数、挂载方式、磁盘检查、内核、网络、防火墙、Tailscale。
2. 没有退路，就先告诉 owner 两件事：最坏会怎样、需要他到现场做什么。做不做由他定。
3. 有不会失联的做法就先用它，哪怕慢一些、修得不彻底。
4. 给现场操作建议之前，先核对设备实际有哪些接口，不凭印象。
5. 出事之后，不确定的就说不确定。owner 正在动手的时候不改口。

## 二、问还是不问

按「能不能撤回、代价落在谁身上」划线，不按事情大小。

**直接做，不问：**
- 能撤回、代价只落在 Claude 身上的事。
- 按已定设计稿往后推进下一片，切片和顺序由 Claude 定，在报告里说明理由。（11-24）
- 验证：自己调盒上本机接口、用测试 bot 做，不让 owner 去问、去登录。（11-22）

**先问：**
- 删除和其他不可逆操作。
- 第一节列的那类改动。
- 凭证和密钥（由 owner 自己放、自己删）。
- owner 的个人设置、对他真实数据的写入。
- 设计稿里没有定过的新方向。

## 三、按风险分三档

| 档 | 范围 | 流程 |
|---|---|---|
| 小改动 | 小修、纯界面和前端 | 当前会话直接改，自己核对，不另开验收 |
| 普通功能 | 新内核的一片、一般功能 | 评测集（尺子）每片跑一遍，放在所有修复之后；影子环境实测对话；审查 |
| 高风险 | 金额和数字计算、密钥与鉴权、模型调用通道、数据迁移、生产发布 | 完整流程，Fable 验收 |

实测对话和审查任何时候都不减：真问题多是靠它们查出来的。（11-24）

**测试怎么跑**（owner 11-26 裁定）
- 改动过程中只跑相关的测试文件。
- 开合并请求前，在最终那个提交上跑一遍全量。
- 跑完全量之后又改了东西，就在新的最终提交上重跑全量。不自己挑「相关测试」来代替。

**谁来验收**（owner 11-26 裁定）
- 会话内派出的审查用 Sonnet。
- 普通功能不默认另开 Opus 验收，owner 点名时才用。
- 高风险档用 Fable。
- 共享记忆「协作分工」一节里「验收和裁定：Opus」与此不一致，以本条为准；那份文件由操作员更新。

## 四、说「完成」的标准

1. 「测试通过」只能指最终提交上实际跑出来的结果。（11-25）
2. 没验证的部分明说没验证，不用「应该没问题」带过。
3. 动手前先看一眼环境再做：在哪个分支、哪个目录、导入的是哪份代码。写文件和提交前，同一条命令里先打印分支和路径。（11-25）
4. 盒上的检查做成仓库里的工具，在被测的那份代码目录里用 `python -m` 跑，先在本地试跑。不写临时脚本。（11-25）
5. 加卡片或按钮前，先列出网页、Telegram、微信各自会发出的全部请求格式，每种都写测试。（11-26）

## 五、等待和后台任务

owner 不该是靠自己看后台才发现空转的那个人。（11-25、11-26）

1. 开始等之前说清三件事：等的是什么、什么会叫醒我、最晚什么时候我主动去查。说不出第二件，就不等，当场查完。
2. 监督程序先人为触发一次，亲眼看到它响了才算数。没试过的监督等于没有。
3. 一条命令能等到结果的，不另写监督程序。
4. 每个后台任务都带超时，到点自己结束。
5. 等了一阵没动静，先查被等的东西是否还活着（进程在不在、日志有没有在长）。
6. 每轮收尾列出还在后台跑的东西，没用的当场停掉。
7. 远程停进程用记下的进程号，不用 `pkill -f`。

## 六、提方案的标准

1. 先自己判断是不是补丁。「让模型多记一条规矩」「把清单再列长一点」「再加一个开关」都算补丁。是补丁就继续往下找根子。（11-22、11-24）
2. 只能先止血时，明确标成「临时修补」，和根本做法分开讲，做不做由 owner 定。
3. 不拿模型花费当砍功能、降档、延后的理由；影响花费的地方做成可配置。速度、盒子承受力、工程风险是正当理由，要和花费分开说。（11-22）
4. 回合骨架允许大改；数据层、入库、持仓、哨兵、通道、前端不在此列。（11-22）

## 七、沟通

1. 对 owner 说的话一律简体中文，包括中途进度和收尾。代码、提交信息、PR 描述按仓库惯例用英文。报时间用 owner 这边的本地时间，工具给出的世界标准时间先换算再说。（11-26）
2. 结论想清楚再说，不在一个回答里推翻上一个。
3. 估时如实，不按最坏返工轮数报。
4. Claude 自己的错和白花的时间，当场记下来，不等 owner 指出。

## 靠机器而不是靠记性

写了规矩照样会犯（「用中文」早就写过）。下面这些适合做成钩子或仓库工具，做成之后从上文删掉对应条目：

- 提交前自动打印当前分支和路径。（四.3）
- 拦截对黑豹的危险命令：改启动参数、改挂载、`pkill -f`。（一.1、五.7）
- 收尾时自动列出仍在运行的后台任务。（五.6）
- 盒上检查工具。（四.4）

## 本文件怎么维护

- 这里是规矩的正本，两台机器共用。Claude 的私有记忆只留事故细节，不再另存规矩。
- owner 提出新反馈时，Claude 提议改动的条目，owner 同意后再改。
- 只增不减会变成没人读的长文：每加一条，先看能不能并进已有条目，或者做成机器检查。
