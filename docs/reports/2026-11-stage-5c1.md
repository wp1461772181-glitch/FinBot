# 5c-1 值得知道以上的异动带原因；值班开始发送

计划：`docs/superpowers/plans/2026-11-27-stage5c1-cause-followup.md`。设计稿 §7.2「异常必有解释」、§7.3 第 7 条。

## 做了什么

- 盯盘提醒叫醒它时，「用户与这件事的关系」里多一项 `tier_label`：哨兵定的级别是 1 时写「值得知道」，2 时写「重大」，其余不写。
- 值班提示词多一段「异动的原因」：有 `tier_label` 时，先查这只股票（合并提醒查整组）最近的公告和新闻；查到了就现在告诉他，第一句说是哪条提醒，第二句说原因和出处；查过没找到也告诉他，直说查了什么、没找到，不猜；只有上次已经讲过同一件事的原因、又没有新进展时才可以不发。
- 新工具 `python -m scripts.wake_replay`：在影子库上把一条旧提醒重新叫醒一次，打印它的决定、理由、要发的话、用时和用到的工具。不载入影子环境就拒绝运行；永远以 `shadow` 模式跑，不会发出任何消息；哨兵库只读打开。
- 发布后把线上的 `FINBOT_DUTY_MODE` 从 `shadow` 改成 `on`，「马上告诉」的消息经发件箱按通道偏好发出，微信也能收到。
- 夜里压住的提醒（北京 0–8 点不响铃、等早 8 点汇总的那些）：它照样被叫醒判断，但事实里写明 `already_sent: false`，提示词说明这时选「马上告诉」也不会在夜里发出；代码对这种情况不投递，记 `delivery=held_night`。这些跟进要等 5c-2 的早间简报才带上。夜里会响铃的提醒（重仓下跌、加急规则等）不受影响，跟进照常当场发。
- 「最近已经告诉过他的」只算真正发出去的消息（`mode=on` 且 `delivery=queued`）。影子模式、超过当日上限、通道没绑定、夜里留下的都不算。

5c 的其余两片：5c-2 由它写早 8 点简报（含「今天替你过滤了 N 条」），5c-3 漏报自查和每条提醒的「有用／没用」。

## 有意没做

- **哨兵的提醒里不写「原因还在查」。** 设计稿 §7.3 第 7 条建议这样写。但哨兵不知道这次唤醒会不会成：API 可能不在、当天的值班条数可能用完、模型可能失败。写了就是一句有时兑现不了的承诺。现在由跟进的那条消息自己说明是关于哪条提醒的。
- **不用代码检查它有没有给原因。** 准则 1：提示词说清楚他需要什么；它选了别的，`reason` 里会写为什么。

## 验收（Fable）

结论「修了再发」，四项：

1. 夜里压住的提醒会被当场跟进，绕过夜间免打扰：已修（见「做了什么」）。
2. 「已经告诉过他的」混着没发出去的消息：已修。
3. 发布步骤：rag-slim 从 `/opt/finbot/rag-slim` 运行（已在盒上核对 `WorkingDirectory`），换树不影响它；运行时文件改成整目录搬运，并逐个核对了线上树里不在 git 的文件（只有 `.env` 和 `data/` 下 9 个，没有 `config/models.yaml`）；`-wal`/`-shm` 随目录搬运，不存在也不会出错；回退步骤写明要带回运行时文件。
4. 回放工具只比较两个环境变量：已加库名必须是 `finbot_ruler` 的检查。

验收提出、这一片不处理、上线后观察的：
- 同一价位反复触发（1 级）时，会不会每次都发「查了没找到」。当日上限 10 条兜底。
- API 长时间不在、恢复后哨兵补投 24 小时内的事件时，可能对几小时前的提醒发跟进。
- 后台值班栏把 `held_night` 显示成「发送失败」（`frontend/src/backstage-view.mjs` 只认 `queued`、`capped`）。随后单独一个前端小 PR 改成「夜里压住，没发」。

今晚的预期：北京 22:30 到 24:00 的 1/2 级提醒会有跟进发出；0 点以后，除会响铃的以外都只留记录，要到 5c-2 才随早间简报送达。

- 发布前备份：`set -a; . /opt/finbot/backup.env; set +a; /opt/finbot/bin/finbot-db-backup.sh`。
- 换树：新代码解到 `/opt/finbot/src-new`；停 telegram、wechat、sentinel、api；`cp -a src/.env src-new/`，`rsync -a --exclude '*.lock' src/data/ src-new/data/`；`mv src src-old99; mv src-new src`；先起 API 等 `/health`，再起 telegram、wechat、sentinel；五个服务都要 active。
- 打开发送：`/opt/finbot/src/.env` 设 `FINBOT_DUTY_MODE=on`（只此一行），只重启 API。
- 回退发送：改回 `shadow` 再重启 API。
- 回退代码：停四个服务，先把当前树 `data/` 的运行时文件同样搬回 `src-old99`（否则哨兵库倒退，提醒编号重用，值班按编号去重会跳过新提醒），再换回。**不搬 `.env`**：旧树里那份没有 `FINBOT_DUTY_MODE=on`，旧代码在 `on` 下会对夜里压住的提醒当场跟进。

### 值得注意的地方（不严重，不在这次处理）

1. **条数偏多。** 22:30 到 23:23 之间，他一共收到 10 条：哨兵自己 6 条，值班跟进 4 条。其中 ANT（没持有，只在研究队列里）占 5 条：哨兵 3 条，跟进 2 条。按准则不算刷屏（每条都有新内容，当日上限 10 条没碰到），但半日市第一个小时就有这么多，值得问 owner 觉得多不多。
2. **新闻工具参数错了，模型没被告知错在哪。** 78 号调 `search_configured_news` 时多传了一个 `days_back`（这是 `web_research` 的参数），返回 `invalid_arguments`，提示只说「请修正参数」，没说是哪个参数。模型没有重试，改用网上搜索，结论没受影响。但给 owner 的话写成了「新闻源这次没有返回 ANT 的匹配内容」，其实是调用出错，并不是查过没有。根本做法是让参数错误的返回写明错在哪个字段、这个工具接受哪些字段，模型就能自己改了重试。属于新的一片，待 owner 定。
3. **「早上那条」。** 78 号的消息说「早上那条只是涨 4.1%」，指的是 22:36 那条。美东时间是早上，北京时间是晚上。小毛病，先记下，再出现就查一下给它的时间是哪个时区。
