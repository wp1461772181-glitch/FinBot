# 阶段 1e：主动消息的通道层

日期：2026-11-24。分支 `claude/kernel-stage1e`。

## 结论

- **提醒、简报、财报通知、bot 自己的通知，现在可以发到微信了。** 此前这些「主动消息」只进一个 Telegram 专用的发件箱。
- **发不出去会换通道。** 一条消息在一个通道上连续失败三次，或者排队超过五分钟（那个桥停了、微信登录失效），并且另一个通道能接，就关掉原来那条、改走另一个通道。关掉的不会事后补发。
- **每条主动消息有投递记录**：发到了哪个通道、成功还是失败和原因、你之后有没有在那个通道上出现过。设置页列出最近 20 条。
- **默认不变。** 不设置时仍然只发 Telegram，行为和上线前一样；Telegram 桥停再久，恢复后提醒照样发出，只发一次。
- **微信的实际发送没有测过。** 微信登录只有线上那一份，影子环境测不了。上线后要在真实账号上发一条看结果。

## 做了什么

1. **发件箱不再绑定 Telegram**（`app/channels.py`）。每条消息带一个通道；按 owner 的偏好决定发到哪；一条消息在多个通道上的记录归为一组，每日上限按「条」算，不按记录数算。
2. **两个桥**：微信桥每 5 秒取一次属于自己通道的消息发给 owner；两个桥都负责清理滞留消息，并在 owner 发来消息时把之前发出的标成「你之后来过」。对话的收发路径没有改。
3. **设置页**「主动消息发到哪里」，三选一：只发 Telegram；先发微信、发不出去再发 Telegram；微信和 Telegram 都发。下面显示两个通道的连接状态、选的通道发不出去时的提示、最近的投递记录。截图（样例数据）：`docs/reports/2026-11-stage-1e/channels-card.jpg`。

没有重写两个桥：对话本来就能跨通道工作（从哪个通道问就从哪个通道答，都进同一条对话线）。

## 各种情况下 owner 会收到什么

选了「先发微信，发不出去再发 Telegram」之后：

| 情况 | 结果 |
|---|---|
| 正常 | 约 5 秒内在微信收到一次 |
| 微信桥停了 | 5 分钟后在 Telegram 收到一次；桥恢复后不会在微信补发 |
| 微信登录失效 | 新消息直接走 Telegram；失效前已排队的等 5 分钟后转 Telegram |
| 微信连续三次拒绝 | 约一分钟内在 Telegram 收到一次 |
| 长消息发到一半失败 | 微信上有前半截，记录显示「只发出了一部分」，完整内容转到 Telegram |

选了「都发」之后：两边各收到一次，每日上限只扣一次；一边发不出去而另一边已经发出时，滞留的那条 5 分钟后关掉，不会事后补发。

## 验证

- 测试：发件箱、两个桥、接口共 360 项相关测试通过（发件箱的测试跑在真实的 PostgreSQL 上，包括两个进程同时清理滞留消息的情形）；全量 Python 测试通过，失败的只有一直存在的那两个。前端 1002 项测试通过，构建干净；设置页的卡片用样例数据单独渲染看过两种状态。
- 没有在盒上做任何实测：这一片不涉及模型，影子环境里也没有桥在跑。

## 审查里查出并修掉的

1. **默认设置下，Telegram 桥停五分钟以上，提醒会被直接丢掉**（计划里写的是「排队超过五分钟就关掉并换通道」，没有别的通道可换时也照样关掉了）。改成只有确实转到了另一个通道才关。
2. **一条消息可能两边都收到**：桥正在发送时，它恰好被判为滞留并转到另一个通道。改成桥取走消息时打一个 180 秒的记号，期间不会被判为滞留。
3. **超过 1800 字的消息在微信上分段发，后面一段失败会整条重发**，前面的段会重复收到。先改成「发出一部分就算发出」，总审查指出这样会悄悄截断，最后改成记为「只发出了一部分」并把完整内容转到另一个通道。
4. **「都发」时，停掉的那一边会攒下旧消息，恢复后一次性补发。** 改成另一边已经发出的就关掉。
5. **「你之后来过」可能是假的**：桥重启后先补发积压消息，再读到 owner 更早发来的消息，会把刚发出的标成已确认。改成以 owner 那条消息自己的时间为准。
6. 微信登录失效期间不再把微信当成可用通道；设置页在所选通道发不出去时明确提示；投递记录加载失败不再让整张卡片消失。

## 没解决的和没验证的

- **微信的主动推送到底送不送得到，没有验证。** 接口返回成功不等于手机上收到，隔了很久之后的推送尤其不确定。要在真实账号上试。
- **微信消息自己的时间在哪个字段里，文档里没有。** 现在读不到就用桥收到消息的时间。加了一行只记字段名的日志，owner 在微信上发一条消息后就能确认。
- **没有做「紧急消息没被确认就升级到下一个通道」。** 现在没有任何来源会把消息标成紧急，要等提醒规则重新设计之后才有。
- **「已送达」没有单独记录。** Telegram 和微信的机器人接口都不告诉我们对方读没读。
- **设置页上的「微信：已连接」只反映登录状态文件，** 不代表微信桥这个进程正在运行。
- **发送成功但随后写库失败时，这条消息会被再发一次。** Telegram 桥一直有同样的窗口。
- **真实的设置页没有人看过。** 我只把卡片单独渲染出来看了。
- **上线顺序要注意**：两个桥都换成新代码之后，才可以在设置里改偏好。旧的 Telegram 桥不认识「通道」，会把属于微信的消息发到 Telegram。部署是整树替换后先起 API 再起两个桥，正常情况下不会碰到。
