# 5d-3a 回答的「好／不好」存到服务器

计划：`docs/superpowers/plans/2026-11-27-stage5d3a-answer-feedback.md`。设计稿 §10.2「每条回答可以点『好／不好』，点『不好』时可以说一句原因」，§9.2 筛选「被点了不好的」。

## 为什么

网页上回答下面的好坏按钮原来只存在那个浏览器里（localStorage），服务器从来没收到过，后台、每周自检、尺子题库都读不到。这一片把它变成存在服务器上的数据，5d-3b「质量」栏和 5d-3c 每周自检都读它。

## 做了什么

- 新表 `answer_feedback`：每条回答（一轮的最终回答）一条记录；改成另一个就覆盖，同一个再点一次不变（新写的原因会替换旧的），网页上再点同一个按钮就撤回。原因一行、最多 200 字，只跟「不好」一起存。
- **网页：** 按钮改成发给服务器，显示服务器上的状态；点「不好」后出一行「哪里不好？（可不填）」，可以发送或跳过；没存上会说「没记上，请再试一次」，按钮保持原样。按「对话 + 轮次」定位，刚答完、还没同步的回答也能点。这个浏览器里以前存的好坏，对服务器上还没有评价的回答上传一次，然后删掉本地记录。游客的按钮照旧只存在浏览器里。
- **在对话里说一句（任何通道）：** 新内核加了一级操作 `rate_answer`。你说「刚才那个回答不好，没说是哪天的价格」，它记下上一条回答为「不好」并带上原因，说明记的是哪一条，然后照常改正。Telegram 和微信都走这一句，不在每条回答下面加按钮。旧流程的 bot 没有这个操作（第六阶段会退掉旧流程）。
- **后台「回答」栏：** 每行标出「你点了好 / 你点了不好」，加了筛选「被点不好的」，详情里显示你的评价和原因。

## 影子环境实测（11-27 12:00 的线上备份）

- **对话里说一句：** 先问「苹果现在股价多少？」，再说「刚才那个回答不好，没说是哪天的价格」。
  - 第一版：模型没有记下评价，直接改正了回答。工具说明只写了「记下他说的好坏」，没说清楚「抱怨上一条回答」也算评价。按准则「提示词里没写明的规则不算数」，我在说明里写明：他说上一条不好、不对、没说清，就是在评价它，先记下「不好」（原因用他的话），再照常改正；这些评价进质量统计。
  - 改后：它回答「已记下：上一条回答标为『不好』，原因是没说明是哪天的价格」，然后把日期补清楚了；库里那一条记在上一条回答上（不是正在写的这条），通道记为「对话里」。
- **网页这条路（以你的身份调接口）：** 点好 → 改不好并写原因 → 后台「被点不好的」筛出它、详情有原因 → 撤回后不再出现。「好」带原因会被拒绝（422），不存在的轮次返回 404。

## 审查（Sonnet，有条件通过）后修的

- **前端请求没有测试：** 把请求的拼法（地址、请求头、请求体）挪进纯函数 `feedbackRequest`，接口封装只负责发出去，补了测试。
- **浏览器旧记录上传可能盖掉更新的评价：** 页面打开后你在对话里或别的设备上评价过，这条回答在页面上仍显示「没有评价」，上传旧记录会把新的盖掉。现在上传带 `if_absent`，服务器上已经有评价就原样保留并返回，按钮显示服务器上的那个。
- **误记风险：** 说明收窄为「他评价你上一条回答本身」才记；他回答你的提问（你问「是指苹果吗」，他说「不对，是微软」）、纠正他自己的问题或接着往下问，都写明不算评价、不要记。
- 找上一条回答时最多读最近 200 行；后台回答栏读评价失败时整栏照常显示，只是没有评价。

**留作已知边界：** 页面上的按钮不会实时反映你在对话里刚说的评价（刷新后才同步）；这只是显示滞后，下次按按钮仍以服务器为准，不会写坏数据。并发两次按下同时插入的冲突分支只靠代码保证，没有专门的测试。

## 没有实测的

- 网页上按钮和原因输入框的实际样子与手感：做了类型检查、构建和单元测试，没有在真实聊天页里点过（要你本人登录）。
- 浏览器里旧记录的一次性上传：只有单元测试；要你下次打开网页时才会发生。
- Telegram、微信上真说一句：有单元测试（这句话原样到 bot、直接记下、不出卡片），没在真实通道上试。

## 和计划不一致的地方

- 计划写按消息编号定位；网页上刚答完的回答还没有消息编号，改成按「对话 + 轮次」定位，由服务器找那一轮的最终回答。
- 工具说明加了「抱怨上一条回答就是评价」这一句（见上）。
