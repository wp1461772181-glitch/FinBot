# 5c-2b 哨兵的价格提醒也能发到微信

计划：`docs/superpowers/plans/2026-11-27-stage5c2b-alerts-to-wechat.md`。

## 做了什么

- 哨兵每发一条提醒，都会通知 API（值班判断就是这样被叫醒的）。现在 API 收到时，按你的通道偏好往发件箱放一份**微信副本**，由微信桥发出。哨兵自己那条路（只用标准库、直接发 Telegram、「收到」按钮、Pushover 升级）一行没动，仍是保底通道。
- 什么时候发副本：

| 你的通道偏好（设置 →「主动消息发到哪里」） | 微信副本 |
|---|---|
| 只有 Telegram（默认） | 不发 |
| Telegram 在前、微信作后备 | 不发：Telegram 那份哨兵已经发了 |
| 微信在前，或只有微信 | 发 |
| 「全部都发」且列了微信 | 发 |

- 不发的情况：夜里压住的提醒（随 8 点汇总和早间简报到你手上）；微信没登录或登录失效；同一条提醒已经复制过（哨兵会对同一条提醒重复通知）。
- 副本不受机器人每天提醒条数的限制；发不出去时**不会转到 Telegram**（那里已经有一份）；在微信桥长时间不在时，超过 30 分钟的副本直接作废、不再补发（价格已经过时）。
- 后台「提醒投递」里这类行的来源写「盯盘提醒」。
- 微信上对这些提醒的「有用／没用」用 5c-3c 的「对话里说一句」。

## 对你现在有没有变化

**没有。** 线上没有存过通道偏好，用的是默认的「只有 Telegram」。要在微信上也收到价格提醒，在设置里把微信排到第一，或选「全部都发」。你的微信登录目前正常。

## 和计划不一致的地方

- 复制出错时留一行 `failed`（验收指出：哨兵拿到 202 就删掉事件，不会有人重试，所以要让这次没发成看得见）。
- 偏好不要副本、提醒又是夜里压住的，按「不要」处理，不留行（否则默认偏好下每条夜间提醒都会留一行）。
- 加了「超过 30 分钟不再补发」（计划没写）。三处都按提醒**自己发出的时间**算：
  - API 停摆后哨兵补投的旧通知（最多积 24 小时）：不复制，记 `skipped_stale`（验收查出的阻断项：起初用的是 API 收到的时间）；
  - 微信桥掉线时排着的副本：清理任务关掉；
  - 微信桥回来后先发后清：取待发的行时就先关掉过时的副本。
- 英文界面写 "Market alert"，和已有的译法一致。

## 验收（Fable）

结论「修了再发」，阻断是上面说的补投旧通知；同时改了：微信桥回来先发后清的那条路、出错留 `failed` 行、值班看「最近发给他的」时不算这些副本（它们和原提醒重复，连发时会占满那 10 个位置）。

还要你知道的：
- 设置里「先发微信，发不出去再发 Telegram」这一项，对价格提醒来说是**两边都到**：Telegram 那份是哨兵自己发的。
- 微信上的副本没有「收到」按钮；会升级的提醒在你只看微信时，仍会在 Telegram 重发或经 Pushover 响铃，除非你在对话里说一句（5c-3c，算「收到」）。
- 选「Telegram 在前、微信作后备」时，哨兵自己的 Telegram 发送失败不会落到微信（哨兵那条路不经发件箱）。

## 没有实测的

- 影子环境不跑微信桥，所以没有看到微信上实际收到的样子；判断、去重、不转发、过期关闭都由单元测试覆盖。真正的检验要等你打开微信偏好后的第一条提醒。

## 测试

- 相关测试（副本规则表每一行、发件箱不转发与过期、接口照常 202、前端来源标签与多语言）全过。
- 全量、尺子：结果写在 PR 描述里。

## 发布与回退

- 照前几片整树替换；新表 `sentinel_copy` 在 API 启动时自动建；哨兵代码没改。不转发和过期的逻辑在两个桥的进程里跑，所以 API、Telegram 桥、微信桥必须一起换到新代码（整树替换本来就是四个服务一起重启）。
- 回退代码：同前；回退后不再复制。注意旧代码不认识这类副本：还在排队、又卡住超过 5 分钟或连续 3 次发送失败的副本，会被旧代码转到 Telegram（多一份）。回退前先看发件箱里有没有待发的「盯盘提醒」行，有就等它发出或手动关掉。
