# 5c-2 早间简报：由它来写

计划：`docs/superpowers/plans/2026-11-27-stage5c2-morning-brief.md`。设计稿 §7.1 第 2 条「攒进下一次简报」、§7.2「沉默也留记录」。

## 做了什么

- 每天北京 08:05 起，它写一份早间简报，经发件箱发出（按通道偏好，微信也能收到）。内容：
  - 值班时选了「攒进简报」的提醒；
  - 5c-1 里夜里写好、但因为夜里不打扰而没发出的原因跟进（`held_night`）；发出后这些行记为 `briefed`，值班以后会把它们算作「已经告诉过他」；
  - 末尾一句由代码写的过滤说明：「另有 N 条提醒我看过，判断不用打扰你（a 条只记下，b 条不理会），在后台『值班』里能看到。」
- 哨兵 8 点的「夜间汇总」不动：它是不经模型、只发 Telegram 的保底通道。简报在它之后，说这些事意味着什么。
- 窗口：从上一份写成的简报开始；没有就往回 24 小时。08:05 到 12:00 之间都可以补写；中午以后才起来的盒子当天不写，第二天的简报覆盖。
- 什么都没发生：不发。只有被过滤的：不调模型，只发那句过滤说明。模型失败、超时或没写出正文：照样把留给他的提醒和跟进原样列出来发出，不会丢。
- 模式跟着 `FINBOT_DUTY_MODE`；发件箱来源 `brief`，不占值班每天 10 条，也不受机器人的提醒上限限制。
- 每天一行记录在新表 `duty_brief`（同一天只写一次，两个进程也不会重复）；这一轮存在隐藏的值班对话里，后台能打开。
- 后台「提醒投递」的来源列认识「值班」「早间简报」；英文界面有对应词条。
- 回放工具 `python -m scripts.brief_replay`：只在影子库上跑、永远是 `shadow`，`--write-sample` 写一组样例值班记录。

## 和计划不一致的地方

- 提示词多了一条「写成纯文本、不要 Markdown、开头不写标题或日期」。第一份影子简报开头是「【早间简报】**早间简报（2026-11-26）**」：重复的标题、模型自己猜的日期、会原样显示的星号（发件箱按纯文本发）。
- `brief` 加进了不受机器人提醒上限限制的来源（计划本意如此，实施时漏了；补了测试，并确认去掉后测试会失败）。
- 窗口里只有已经发出的或没完成的记录时也不发（否则会发一条只有标题的空消息）。
- `run_once` 多了 `day=`、`since=` 两个参数，只给回放工具用。

## 影子实测（11-27 的备份）

| 回合 | 资料 | 结果 |
|---|---|---|
| 真实值班记录（11-24 到 11-26，往回 80 小时） | 攒进简报 1 条（INTC 反弹）、只记下 1 条 | 写成，18.6 秒、2 次模型调用；它查了最新持仓，指出提醒里「占总资产 40.9%」和账户的 6.2% 对不上 |
| 样例记录（改了提示词之后） | 攒进简报、夜里压住的跟进、只记下、不理会各 1 条 | 写成，18.0 秒、2 次模型调用；纯文本、没有自己的标题；样例里的价格是虚构的，它查了行情后如实说「对不上、无法确认」，没有照着复述 |

- 40.9% 那一条是回放的时间差：提醒发出时账本里只有英特尔，11-26 记了苹果和特斯拉之后占比才降下来。它的做法（把出入摆出来、让他以账户为准）是对的。
- 样例数据是虚构的，所以这两份只能看流程和格式，评判不了内容。第一份真简报是北京 11-28 08:05（覆盖 11-27 的半日市）。

## 验收（Fable）

第一轮结论「修了再发」，阻断两项、建议六项，全部改了：

1. 后台把简报带出去的跟进（`briefed`）显示成「发送失败」：改成「已随早间简报发出」。
2. 简报没能排进发件箱时也记 `done`、窗口前移，夜里压住的跟进会永久丢掉：改成记 `failed`，下一份简报补带；测试覆盖「第一天没通道、第二天补带并标 `briefed`」。
3. 模型不知道现在几点：代码把北京时间的「现在」、窗口起点和每条记录的时间交给它；提示词要求说到时间用资料里的北京时间。
4. 第一份或前几份失败时窗口会漏：没有写成过的简报时，从最早一行简报记录往前 24 小时算。
5. 每分钟一次必然冲突的插入：先查当天有没有行。
6. 「8 点已经发了夜间汇总」是无条件的：改由代码按窗口里有没有夜里压住的提醒告诉它（`night_digest_sent`）。
7. 过滤说明写明窗口的起点（北京时间），如「从 11-27 08:05 到现在，另有 3 条……」。
8. 总时限 180 秒和循环自己的收尾一样长：放宽到 240 秒。

第二轮结论「可以发布」，另提四条小问题，也都改了：过滤说明直接写窗口起点；提示词里 `night_digest_sent` 为 false 时改成「不确定有没有这份汇总，不要提到它」（这个值是按窗口里有没有夜里压住的提醒推断的，不是读哨兵库）；简报已排进发件箱后再出错仍记 `done`，次日不会整份重发；英文界面补了「夜里压住，没发」「已随早间简报发出」。

验收提出、留给 owner 或以后看的：
- 只有被过滤的日子也会发一条「另有 N 条……」。设计稿要的就是这句（让他知道它在干活），先保留；如果嫌吵，可以改成只在周末汇总或只在 N 较大时发。
- 被当日上限挡住或没发出去的「马上告诉」，简报不带也不计数。
- 08:00 前后入队、08:05 之后才判完的夜间提醒，要等下一份简报。

## 发布与回退

- 照 5c-1 的步骤整树替换（备份；新树解到 `src-new`；停四个服务；`cp -a .env`、`rsync -a --exclude '*.lock' data/`；换树；先起 API 再起其余三个）。
- 新表 `duty_brief` 在 API 启动时自动建。
- 关掉简报：没有单独的开关，跟着值班模式；只关简报不关值班要另加开关（目前没有需要）。
- 回退代码：同 5c-1，搬回 `data/` 运行时文件，不搬 `.env`。已排队的简报回退后仍会发出：两个桥按通道取待发的行（`app/channels.py` `pending`），不看来源。旧代码不会再写新简报；`duty_brief` 表留在库里，无害。
