# 盒上补上知识库的「存」这一头

计划：`docs/superpowers/plans/2026-11-28-box-knowledge-indexing.md`。owner 11-28 要求「写方案然后执行」。

## 为什么停在 11-03

- **只搬了「查」这一头。** 11-13 搬到盒上时，瘦后端 `finbot-rag-slim` 只做检索和重排。它调 OpenRouter 的 bge-m3 给问题做向量，查的是 pgvector 的 `chunks` 表。
- **「存」的链还留在 Mac 上。** 同步 → 切块 → 向量化 → 写入，这条链原来在 Mac 上跑，用的是本地 BGE-M3 和 Milvus。盒上缺三样东西：本地模型运行时、分词器、能写 pgvector 的代码。
- **连同步循环都没有启动。** 同步循环要先有本地模型运行时才会启动，所以新文档连知识库都没进，不只是没做向量化。

## 做了什么

- **入库组件 `app/knowledge/box_index.py`。** 给现有的同步、切块和索引任务换上盒上能用的三个零件：
  - **分词器：** 用 `tokenizers` 读 bge-m3 自己的 `tokenizer.json`。本机测试里和 transformers 的计数逐个比对，完全一致；盒上同一句话两边都数出 17 个 token。
  - **向量化：** 调 OpenRouter 的 `baai/bge-m3`。抽 4 块已有文本重新算，和库里原来的向量余弦相似度都是 1.0，新旧向量放在一起用没有问题。
  - **向量库：** 写 pgvector 的 `chunks` 表，列和瘦后端读的一一对应，按 `id` 覆盖写入。
- **后台循环 `knowledge-index`。** 每 2 分钟一轮，依次做：
  1. 先核对表里只有当前这一代，不是就整轮跳过；
  2. 各类来源各同步一小批；
  3. 有块要入库时，先发一个字试探向量化服务。不通就等下一轮，免得把这些块的重试次数用光；
  4. 最多入库 40 块。

  组件只在第一次加载，之后复用。缺文件或缺依赖时只记一行日志，什么都不做。连着影子库又要写线上表时，拒绝写入。开关 `FINBOT_KNOWLEDGE_INDEX`，默认开。
- **密钥不复制。** OpenRouter 的密钥和 pgvector 的登录信息，从盒上已有的 `/opt/finbot/rag-slim/env` 和 `/opt/finbot/pgvector.env` 里读，不打印、不另存。
- **用量记账。** 每次向量化调用记进模型用量账本，用途是「知识库」，任务名 `knowledge-index`，带 token 数。
- **手动工具 `python -m scripts.knowledge_index_once`。** 用法：
  - 默认只在影子环境跑，而且不能写线上的 `chunks` 表；要写线上表，必须加 `--live`；
  - `--retry-failed` 把因为故障用完重试次数的块放回队列；
  - 跑完打印写了多少块、用了多少 token、按标价合多少钱。
- **盒上的准备工作。** API 的环境里装了 `tokenizers` 0.23.3，并顺带装了 huggingface-hub 等几个依赖。分词器文件从 Mac 拷到 `/opt/finbot/knowledge/bge-m3-tokenizer.json`。

## 影子实测（11-28 11:05 的备份；写的是结构相同的 `chunks_shadow` 表，不碰线上）

| 轮次 | 写进 | 向量化调用 | token | 按标价 |
|---|---|---|---|---|
| 第一次，6 轮 | 226 块 | 17 次 | 92,337 | 0.0009 美元 |
| 审查修改后，3 轮 | 120 块 | 12 次（含 3 次试探） | 45,938 | 0.0005 美元 |

- **每块约 400 个 token。** 一份大 10-K 约 600 块，按标价合 0.2 到 0.3 美分。
- **检索查得回来。** 用一句问题向量检索影子表，最相近的三条都是 11-24 才进来的美光委托书。
- **同步不按时间先后。** 它按记录编号推进，所以每轮进来的有新文档，也有日期早的旧资料，最终都会补齐。
- **那 484 块不是故障。** 主库里一直挂着没索引的 484 块，都属于已经停用的旧版本文档，任务已被正确标为「不可索引」。

## 审查（Sonnet）

结论「有条件通过」，提的问题全部改了：

1. **每轮都重新加载分词器（17 MB）和 HTTP 客户端，客户端也不关。** 改成只加载一次、之后复用。
2. **故障会耗光重试次数。** 向量化服务故障或网络断开持续约 8 分钟，这期间每批块都会失败，试满 4 次后就永久停在失败状态。改为每轮入库前先试探，不通就跳过；400、401 这类明确的错误不再重试；手动工具加了 `--retry-failed`。
3. **测试没走真实的索引任务。** 补了一条：用真实的入库和索引任务，配一张假表跑 `PgVectorStore` 的语句，确认回执能被正确确认。
4. **代际不一致时，先同步、后拒绝。** 改成先查代际再同步。
5. **配置文件解析不认 `export` 前缀和行内注释。** 已补上。
6. **疑点：影子环境如果开着后台循环，会写线上向量表。** 影子环境本来就不开后台循环；循环里又加了一道保护，盒上已验证。

审查提到、这次不处理的：
- **只增不减。** 旧版本文档的向量行不会从表里删掉。原来的 Milvus 路径也是这样。API 检索时按主库里「有效且已索引」的块过滤，旧行到不了回答里；但瘦后端的关键词检索是整表建的，会不会因为旧行而变差，在仓库外，没法核实。
- **关键词检索要重启才认新块。** 瘦后端的 BM25 只在启动时建一次。新块入库后，向量那一路马上能查到，关键词那一路要等瘦后端重启。上线补齐后我会手动重启一次。
- **在盒上会不会拖慢对话没有实测。** 每轮要切 5 份文档的块，用的是纯 Python，可能会占用同一进程。

## 上线后发现、已修（PR #76）

工具和后台日志把「这一批扫过的来源数」当成了「新文档数」。同步走完一圈后会从头再扫一遍，没变的来源会被直接跳过、不重新切块，但我仍把它们算成了「新文档」。于是最后几轮显示「新文档 3–17，入库 0 块」，后台日志也会每 2 分钟报一次假的新文档。现在改成按入库函数返回的新文档数和新块数来统计。

CPU 方面不用担心：没变的来源会被直接跳过，不重新切块。补齐期间 API 进程占用约 7% 的 CPU、640 MB 内存。
