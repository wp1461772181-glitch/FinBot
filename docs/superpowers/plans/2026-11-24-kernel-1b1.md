> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 让新内核每个问题先用低档接住、需要时自己升档；一步里的多个工具同时执行；每一步用它自己的话说一句在做什么；高档任务列清单并打勾。本计划只做内核和端点这一侧，把这些作为流事件发出并落库。

**Architecture:** 在 1a 的 `app/kernel/` 上加三样东西：两个内核自带的工具 `escalate`（升档）和 `plan`（清单），以及每个工具都带的可选参数 `say`（说一句）。它们不进工具目录，由内核自己处理，固定出现在工具列表里，所以缓存前缀不变。工具执行从 `loop.py` 挪到新文件 `app/kernel/toolrun.py` 并改成并行。端点把两个新事件 `narration`、`checklist` 转发给客户端，并随最终回答一起落库，历史重载时带回。

**Tech Stack:** 同 1a。不新增依赖。

## Review Focus

1. **并行执行时引用编号乱掉。** 两个工具同时返回，编号必须仍按模型提出调用的顺序分配，同一批输入每次编号相同。→ 任务 1。
2. **一个工具卡住或抛异常拖垮同一步里的其他工具。** 各自独立成败，结果各自交回模型。→ 任务 1。
3. **升档超过 bot 设置的上限，或升到不存在的档。** 夹到上限并如实告诉模型，不报错。→ 任务 2。
4. **模型把 `say` 当成正文写了一长段，或者 `say` 里夹了工具名、换行。** 截到 80 个字、换行变空格，原样显示，不拦。→ 任务 3。
5. **清单里的状态值写错、条目几十条。** 未知状态当作未开始，最多保留 12 条，不报错。→ 任务 3。

### Task 1: 工具执行挪到独立文件并改成并行

**Files:**
- Create: `app/kernel/toolrun.py`
- Modify: `app/kernel/loop.py`
- Test: `tests/test_kernel_toolrun.py`；按需更新 `tests/test_kernel_loop.py`

**Interfaces:**
- Produces（任务 2、3 在此基础上加东西）：

```python
# app/kernel/toolrun.py
MAX_PARALLEL = 4

async def run_step_tools(run, calls: list[dict]) -> list[dict]:
    """Execute one step's tool calls; return one {"role": "tool", "tool_call_id", "content"} message per call, in call order."""
```

- `run` 是 1a 的 `_Run`（把它需要的字段原样带过来；`_Run` 仍定义在 `loop.py`，`toolrun.py` 只按属性使用，不反向 import `loop.py`）。1a 里 `_run_tool`、`_valid_arguments`、`_calculate`、`_number_evidence` 等执行工具的函数整体挪进 `toolrun.py`，行为不变。
- 规则：
  1. 先为这一步的每个调用按顺序发 `tool_start` 事件。
  2. 除 `calculate`、`calculate_formula` 以外的调用同时执行，同一时刻最多 `MAX_PARALLEL` 个（`asyncio.Semaphore`）。每个调用独立：一个抛异常或超时，不影响其他；它自己的结果是 `tool_failed`。
  3. 全部结束后，**按调用顺序**依次做引用编号（`number_rows` 等），然后按调用顺序依次发 `tool_result` 事件。这样同一批输入的编号每次相同。
  4. `calculate`、`calculate_formula` 在其他调用都编完号之后按顺序逐个执行（它们要用到已有的引用）。
  5. 并行执行时不能共享会被工具内部改写的可变对象。先读 `app/agent_workflow/tools.py` 的 `invoke`/`_dispatch`：如果它接收或经上下文拿到本轮的引用列表并往里写，就给每个并行调用一份独立的临时列表，执行完再在第 3 步按顺序合并。
  6. 返回的工具消息顺序 = 调用顺序。

### Task 2: 低档接住，需要时升档

**Files:**
- Create: `app/kernel/tiers.py`
- Modify: `app/kernel/loop.py`, `app/kernel/prompt.py`, `app/kernel/toolrun.py`
- Test: `tests/test_kernel_tiers.py`；按需更新 `tests/test_kernel_loop.py`

**Interfaces:**
- Produces：

```python
# app/kernel/tiers.py
TIERS = ("low", "mid", "high")
EFFORT = {"low": "low", "mid": "medium", "high": "high"}     # what is sent as reasoning_effort
ESCALATE_SCHEMA: dict            # OpenAI function schema of the kernel's own tool `escalate`

def ceiling(bot_effort: str | None) -> str:
    """The highest tier this bot may use: None -> "high"; "none"/"minimal"/"low" -> "low"; "medium" -> "mid"; anything higher -> "high"."""

def clamp(requested: str, top: str) -> str: ...
```

- 规则：
  1. 每一轮从 `low` 开始：第一步用 `reasoning_effort="low"`，不管 bot 设的是什么。bot 的 `reasoning_effort` 只作为上限（`ceiling`）。
  2. 工具列表末尾固定多一个 `escalate`，参数 `depth`（`"mid"` 或 `"high"`，必填）。说明文字（写进 schema 的 description，逐字使用）：`切换到更深的思考档位再继续。问题需要多步推理、比较权衡、给出判断，或者你拿不准时调用。mid 用于一般的分析，high 用于复杂的研究。简单的问题不要调用，直接回答或查一下就答。`
  3. 模型调用 `escalate`：把当前档位设为 `clamp(depth, ceiling)`，之后的每一步都用新档位对应的 `reasoning_effort`。交回模型的结果是 `{"ok": true, "tier": <实际档位>, "note": "已切换到 <档位> 档，请继续。"}`；被上限夹住时 note 是 `"这个助手最高只到 <档位> 档，已按 <档位> 档继续。"`。`depth` 不是 `mid`/`high` 时结果是 `invalid_arguments`，档位不变。档位只升不降。
  4. `escalate` 由内核自己处理，不经 `tools.invoke`，不产生引用。它和同一步里的其他调用一起，按调用顺序返回结果；档位从下一步起生效。
  5. `audit["tier"]` 是这一轮结束时的档位；`audit["escalated"]` 是布尔值。返回字典的 `final_protocol` 里加 `"tier": <档位>`。
  6. 系统说明 `prompt.SYSTEM` 的「怎么做事」一节末尾加一条（逐字）：`- 你现在处于快速档。简单的问题直接回答，或者查一下就答。问题需要多步推理、比较权衡、给出判断，或者你拿不准时，先调用 escalate 切换到更深的档位再继续。用户说「想深一点」「仔细分析」时用 high；用户说「快点」「简单说」时不要升档。`

### Task 3: 说一句，和清单

**Files:**
- Create: `app/kernel/progress.py`
- Modify: `app/kernel/loop.py`, `app/kernel/toolrun.py`, `app/kernel/prompt.py`, `app/agent_chat_stream.py`
- Test: `tests/test_kernel_progress.py`；`tests/test_kernel_wiring.py` 加端到端两条

**Interfaces:**
- Produces（1b-2 的各端按此显示）：

```python
# app/kernel/progress.py
SAY_MAX = 80
PLAN_MAX_ITEMS = 12
PLAN_SCHEMA: dict                       # the kernel's own tool `plan`
def with_say(schema: dict) -> dict: ... # a copy of a tool schema with an optional first property `say`
def take_say(arguments: dict) -> tuple[str | None, dict]: ...   # (cleaned sentence or None, arguments without `say`)
def clean_plan(items) -> list[dict]: ...                        # [{"text": str, "status": "pending"|"doing"|"done"|"failed"}]
```

- 新事件（内核发出，端点转发为同名 SSE 帧）：
  - `{"event": "narration", "text": <一句话>}`
  - `{"event": "checklist", "items": [{"text", "status"}, …]}`（每次是完整的清单）
- 规则：
  1. 发给模型的每个工具定义（目录里的只读工具、`escalate`、`plan`）都经 `with_say`：多一个可选的字符串参数 `say`，排在属性的第一个，说明文字（逐字）：`用一句话告诉用户你发现了什么、接下来做什么。像人说话，不要出现工具名。`。`with_say` 不修改传入的对象。
  2. 执行前用 `take_say` 把 `say` 从参数里取出，其余参数照常校验和执行（工具本身不知道 `say`）。清理：去掉首尾空白，换行变成空格，超过 `SAY_MAX` 个字符截断；空的当作没有。
  3. 一步里第一个带 `say` 的调用，发一条 `narration`；这一步其余的 `say` 丢掉。`narration` 在这一步的 `tool_start` 之前发。
  4. 模型在调用工具的那一步里直接写了正文（1a 里会发 `answer_reset` 丢掉）：现在如果这一步没有任何 `say`，就把这段正文清理后作为 `narration` 发出（仍然先发 `answer_reset`）；有 `say` 就用 `say`，正文丢掉。
  5. 工具列表末尾在 `escalate` 之前固定多一个 `plan`，参数 `items`：数组，每项 `{"text": 字符串, "status": "pending"|"doing"|"done"|"failed"}`。说明文字（逐字）：`复杂任务（已切换到 high 档）开始时，把要做的事列成清单；之后每完成一项，带着完整清单再调用一次，更新各项的状态。简单任务不要用。`。每次调用发一条 `checklist`（完整清单）。交回模型的结果是 `{"ok": true, "items": <条数>}`。`clean_plan`：不是列表当作空；每项取 `text`（去空白、截到 60 字，空的丢掉）和 `status`（不认识的当 `pending`）；最多 `PLAN_MAX_ITEMS` 条。
  6. `plan` 由内核自己处理，不经 `tools.invoke`，不产生引用。
  7. 返回字典的 `final_protocol` 里加 `"narration": [各句话，按发出顺序]` 和 `"checklist": <最后一次的清单或 []>`。
  8. 系统说明「怎么做事」一节末尾再加一条（逐字）：`- 每次调用工具时，在 say 里用一句话说明你发现了什么、接下来做什么，用户会实时看到这句话。切换到 high 档后，先用 plan 列出清单，再逐项去做。`
  9. 端点 `app/agent_chat_stream.py`：`events()` 里收到 `narration`、`checklist` 事件时，转发为同名帧（数据就是事件里除 `event` 外的字段）。最终回答落库时 `final_protocol` 的内容已经会进入那一行的 `tool_calls`（先确认；不是的话照 `trace`、`thinking_ms` 的做法加进去）。`get_messages`（历史重载）返回每条 assistant 消息时带上 `narration`、`checklist`、`tier` 三个字段（没有就不带），做法照它现在带回 `trace`、`thinking_ms` 的方式。
  10. 旧流程不发这两个事件；端点的改动对旧流程的回合没有可见影响。
