**Goal:** 在旧流水线旁边搭出新内核的最小可用版：一个只往后追加的工具循环，回答边生成边显示，按 bot 切换，尺子能选内核；用尺子量出它和旧流程的差距。

## Review Focus

1. **模型在同一步里既写了字又调了工具。** 字已经流出去了。必须发 `answer_reset`，让各端清掉这段，最后落库的回答里不能有它。→ 任务 2、任务 3。
2. **工具循环停不下来**（模型一直调工具）。到步数或时间上限后，必须用一次不带工具的调用收尾并给出回答，不能空手返回。→ 任务 2。
3. **工具抛异常或返回 `ok: false`。** 结果如实交给模型，循环继续；不能整轮失败。→ 任务 2。
4. **模型服务出错。** 可重试的错误重试一次；仍失败就向上抛 `ProviderFailure`，由端点现有的出错处理给用户一句人话。不能吞掉。→ 任务 2。
5. **切换开关误伤旧流程。** 没设 `engine` 的 bot、访客、定时任务（`agent_task_runner`）都必须仍走旧流程。→ 任务 3。

- `run_turn` 的参数含义与 `run_direct_turn(question, context, emit, messages, state)` 相同：`context` 是 `AgentRuntimeContext`；`emit` 是 `async def emit(event: dict)`；`messages` 是端点拼好的消息列表（第 0 条是端点自己的 system，丢掉不用；其余是历史和当前问题）。
- 返回字典的键（与旧流程一致，端点和 `graph.py` 后处理都读它）：`answer`、`citations`（列表）、`status`（成功是 `"succeeded"`）、`reason`（`None`）、`route`（固定 `"K"`）、`audit`（字典）、`final_protocol`（`{}`）、`pending_request`（`None`）、`result_sets`（`{}`）、`previous_category`（`None`）、`previous_scope`（`None`）、`unverified_lines`（`[]`）。
- `audit` 至少有：`terminal_status`（同 `status`）、`engine`（`"v2"`）、`model_calls`、`decision_steps`、`tool_calls`、`token_usage`（各次调用 `total_tokens` 之和）、`cache_read_tokens`、`cache_write_tokens`、`stop_reason`（正常结束 `None`；到上限是 `"step_cap"` 或 `"time_cap"`）。
- 发出的事件（`await emit({...})`）：
  - `{"event": "delta", "text": piece}`：每一步模型吐出的每一段正文，实时发。
  - `{"event": "answer_reset"}`：某一步已经发过正文、但这一步最后带了工具调用时发一次，表示之前的正文作废。
  - `{"event": "assistant_tool_request", "protocol": {"calls": message["tool_calls"], …reasoning 字段}}`：与旧流程同形。
  - `{"event": "tool_start", "call_id", "name", "arguments"}` 和 `{"event": "tool_result", "call_id", "name", "result"}`：与旧流程同形。
- **重要：`graph.py` 现在在回合结束后会自己发一次整段的 `delta`。** 新内核的正文已经流过了，所以返回字典里加一个键 `streamed: True`，任务 3 会让 `graph.py` 在这种情况下不再重发。
- 循环规则：
  1. 工具集 = `READ_TOOLS` 中当前身份可用的那些（`schemas(owner=…, names=READ_TOOLS)`；`context.tool_scope` 不为 `None` 时再取交集）。整轮固定，顺序稳定。
  2. 每步调用 `stream_decision(..., reasoning_effort=context.reasoning_effort, on_text=…, keep_thinking=True, cache=True)`。把返回的 assistant 消息（含 `_anthropic_content`）接到消息列表后面。
  3. 没有工具调用：这一步的正文就是回答，结束。
  4. 有工具调用：若这一步发过正文，发 `answer_reset`；发 `assistant_tool_request`；按顺序逐个执行（1a 不并行）；每个结果作为 `{"role": "tool", "tool_call_id", "content": <json>}` 接到后面；回到 2。
  5. 执行工具：参数是 JSON 字符串，解析失败或 `tools.invoke` 返回 `ok: false` 都如实作为结果交回模型；工具抛异常时结果是 `tools.error("tool_failed")`。`calculate` 和 `calculate_formula` 不走 `tools.invoke`，照旧流程 `execute_read` 的做法直接调用并登记一条 `source_type: "calculation"` 的引用。
  6. 引用：证据类工具返回的行经 `evidence.number_rows(name, rows, citations, scope)` 编号（`citations` 是本轮的列表，`scope` 传旧流程在没有任何限定时使用的那个值），把带 `citation: "[n]"` 的行放进交给模型的工具结果里。不调用 `gate_row`（1a 不做回答前的拦截）。`read_history_citation` 的结果用 `bind_history_citation` 绑定。
  7. 步数到 `MAX_STEPS` 或用时超过 `SOFT_SECONDS`：追加一条 system 消息「系统事实：已达到本轮的查询上限。请用现有资料直接回答；资料不足的部分明说。」，做一次不带工具的调用，其正文作为回答。
  8. 回答定稿后过一遍 `strip_invalid_markers(answer, citations)`；`citations` 逐项过 `persistable_citation`（若旧流程是在 `graph.py` 里做这一步，就不要重复做，照实际情况来）。
  9. 模型调用抛 `ProviderFailure` 且 `retryable` 为真：等 1 秒重试一次；再失败或不可重试，向上抛。重试前如果这一步已经发过正文，先发 `answer_reset`。
  10. 整个 `run_turn` 包在 `decision_session(context.base_url)` 和 `progress_watchdog(…)` 里，做法照 `direct._guarded`。
