# Kernel 1d Implementation Plan — long conversations stay cached, and a failing model hands over to a backup

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** On the new kernel, a turn of a long conversation re-reads almost all of its history from the provider's cache instead of paying for it again, and a turn whose model fails carries on with the owner's chosen backup model and says so.

**Architecture:** The history a turn carries is already budgeted, layered and compressed in the background by `app/agent_context.py` and the endpoint; the kernel inherits that. Two things break caching across turns today: the only cache breakpoint in the conversation is on the last message, which is never a prefix of the next turn; and the boundary between the raw layer and the shortened layer slides by one turn every turn once a conversation is long. This slice (1) marks the end of the carried history as a cache breakpoint, (2) makes the layer boundary move only when it crosses a fixed grid of message sequence numbers, for kernel turns, and (3) adds a `fallback` model role that the kernel switches to when the primary model fails after its retry.

**Tech Stack:** Python 3 (asyncio, SQLAlchemy), pytest; one row in a React settings table.

**Spec:** `docs/finbot-new-kernel-plan-2026-11-22.zh-CN.md` sections 4.1 (「对话越来越长怎么办」) and 4.9 (main checkout, untracked; binding parts copied into the tasks).

## Review Focus

1. A conversation of 300 turns on a kernel bot: from one turn to the next, the messages before the current question are a byte-identical extension of the previous turn's (the previous question and answer appended) on all but a small number of turns, and those turns are exactly the ones where the raw layer's first turn changed or a background summary landed.
2. The first model call of a turn has a cache breakpoint on the last block of the last message of the carried history, and the request never has more than four breakpoints.
3. The primary model fails twice on the second step of a turn that has already run two tools: the backup model continues from the same messages (tool results included), nothing is run twice, and the answer ends with one line naming the backup.
4. No backup model is set, or the backup is the same catalog entry as the primary: the turn fails exactly as it does today.
5. The backup model fails too: the turn fails as today, with a sentence a person can read, and the audit says both were tried.

### Task 1: a cache breakpoint at the end of the carried history

**Files:**
- Modify: `app/anthropic_native.py` (`build_request`, `convert_messages` if needed), `app/kernel/prompt.py` (`build_messages`)
- Test: `tests/test_kernel_model.py`, `tests/test_kernel_loop.py` (or the prompt tests' file)

**Interfaces — produces:**
- A message dict may carry the private key `"cache_point": True`. `build_request(..., cache=True)` puts `cache_control: {"type": "ephemeral"}` on the last content block of the converted message that such a message became (when consecutive same-role messages are merged in conversion, on the last block that came from the marked message). The key is never sent to the provider, and with `cache=False` it is ignored and stripped. At most one marked message is honoured (the last); together with the three existing breakpoints (last tool, last system block, last block of the last message) a request has at most four. When the marked message is also the last message, there is one breakpoint there, not two.
- `prompt.build_messages` marks the last message of the carried history that precedes the current question (the message just before the last `user` message that equals the question; nothing is marked when there is no earlier message, and on the post-press path where the question is replaced by a fact, the message before the fact). Messages after the question (the memory note, the citation catalogue, system notes) are never marked. The mark is set on a copy; the caller's list is not mutated.
- Non-Anthropic providers: the key must not leak into their requests either (strip it wherever kernel messages are handed to `decision_request`).

### Task 2: the layer boundary moves on a grid, for kernel turns

**Files:**
- Modify: `app/agent_context.py` (`layer_rows`), `app/agent_chat_store.py` (`conversation_context`), `app/agent_chat_stream.py` (the one call of `conversation_context` for the turn)
- Test: `tests/test_kernel_history.py` (new), the existing tests of `layer_rows` must pass unchanged

**Background:** `layer_rows` puts the newest complete turns that fit `l1_bytes` in layer 1 (sent whole) and the turns before them in layer 2 (sent shortened), newest that fit `l2_bytes`; the rest is `overflow`, which the next background summary takes over. Layer 2 is sent before layer 1. Once a conversation is longer than layer 1, every new turn pushes the oldest layer-1 turn into layer 2, so the text sent changes at the layer boundary every turn and nothing after it can be read from cache.

**Interfaces — produces:**
- `ANCHOR_GRID = 64` in `agent_context`. `layer_rows(..., anchor_grid: int | None = None)`. With `None` the result is exactly today's. With a grid:
  - A turn is an *anchor* when it is the first complete turn after the summary boundary (`upto`) and the fetched rows reach back to it, or when `first_row.sequence // grid` differs from that of the complete turn before it. Anchors depend only on sequence numbers, so they never change as the conversation grows.
  - Layer 1 starts at the earliest anchor from which the turns fit `l1_bytes` under today's cost rule; turns the old rule would have kept before that anchor go to the front of the older set (layer 2). If no anchor fits (one grid cell alone exceeds layer 1), fall back to today's rule for that call.
  - Layer 2's old end is snapped the same way: it starts at an anchor (the earliest from which the older turns fit `l2_bytes`), and what is before it is `overflow`.
  - Everything else the function returns keeps its meaning.
- `conversation_context(..., anchored: bool = False)` passes `anchor_grid=ANCHOR_GRID` when true.
- The endpoint passes `anchored=True` exactly when this turn will run on the kernel: the same decision `app/agent_workflow/graph.py` makes (`_engine(bot, unattended) == "v2"` and the `FINBOT_KERNEL_V2` flag on). Reuse that function; do not copy its logic.

### Task 3: a backup model

**Files:**
- Modify: `app/agent_model_roles.py`, `app/kernel/loop.py`, `app/kernel/prompt.py` (only if a sentence is needed), `frontend/src/app/settings/models/RoleTable.tsx`, the two locale files
- Test: `tests/test_kernel_fallback.py` (new), `tests/test_agent_model_roles*.py` (existing role tests, extend)

**Spec (4.9, binding):** 模型服务出错或超时：重试一次；仍失败就换到你预先指定的备用模型，并在回答上标明「这条由备用模型回答」。每一种失败都有一句人能看懂的话，不出现错误代码。

**Interfaces — produces:**
- `agent_model_roles.ROLES` gains `"fallback"`. Unlike `earnings` / `forecast` it has no default: `fallback_for(owner_hash) -> dict | None` returns `catalog.resolve(name)` when the role names an entry that is in the catalog, else `None` (unset, or the entry has left the catalog). The existing `/model-roles` endpoints then list and set it with no further change.
- Settings page: one more row in `RoleTable.tsx`, key `fallback`, label 「备用模型」, hint 「对话模型出错或超时、重试一次仍不行时改用的模型；不选就没有备用，那一轮会失败。」, built like the `judge` row (no "server default" wording).
- Kernel (`loop.py`):
  - `_Run` gains `model: ModelUse` (provider, model name, api key, base URL, catalog entry name) initialised from the context, and `fallback_used: str | None`. `_model_step` reads the model from `run.model`, not from the context.
  - When a model call has failed after its one retry (any exception from the provider layer except `asyncio.CancelledError`), and the turn is not already on the backup: look up `fallback_for(context.owner_hash)` (blocking: `asyncio.to_thread`). If there is one and it is not the same provider + model as the primary: switch `run.model` to it, set `run.fallback_used` to its catalog name, emit a system narration 「主模型没有回应，改用备用模型「<name>」继续。」 (`{"event": "narration", "text": …, "system": True}`, also appended to `run.narration`), and make the same step's call again with the backup. Otherwise re-raise as today.
  - On the switch the message list is rebuilt once: every earlier assistant message loses its kept reasoning (the keys starting with `reasoning_`; they belong to the primary model and another model or provider may reject them). Tool calls and tool results stay. Text already streamed in the failed step has been reset by the existing code path; do not emit it twice.
  - The backup stays for the rest of the turn; the next turn starts on the primary again.
  - A failure of the backup (after its own one retry) is re-raised; the endpoint's existing failure notice answers the user.
  - When the turn ends with an answer and `run.fallback_used` is set, the answer gets one last line, emitted as a `delta` and included in the returned and stored answer: `\n\n（这条由备用模型「<name>」回答。）`. The post-press code-written report (`已执行：…`) is not labelled.
  - Audit: `audit["fallback"] = {"from": <primary catalog name or provider/model>, "to": <name>, "reason": <the failure's short code, e.g. provider_timeout>}`; when the backup failed too, `audit["fallback"]["failed"] = True` is set before re-raising (the endpoint stores the audit of a failed turn only if it already does so today; do not add storage). `final_protocol["fallback_model"] = <name>` on success. `audit["calls"]` lines gain `"model": <catalog name>`.
  - The tier's effort is sent to the backup as to the primary; a model that does not take that effort ignores it, as today.
