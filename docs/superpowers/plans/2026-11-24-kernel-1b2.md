# Kernel 1b-2 Implementation Plan — showing the work on the web page, Telegram and WeChat

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** What the new kernel says while it works (its sentences, its checklist, its tier) is visible on all three surfaces, the checklist ticks itself, and a turn that is slow says so.

**Architecture:** The kernel already emits `narration` and `checklist` stream events (1b-1). This slice (a) moves the checklist's bookkeeping from the model to the kernel: tools take an optional `item` number, the kernel derives each item's state; (b) has the kernel fill in a plain sentence when the model wrote none and one when a step is slow; (c) has the endpoint keep the progress of a turn that was cancelled or failed; (d) renders the events on the web page, in Telegram's editable progress message, and as at most two extra messages in WeChat.

**Tech Stack:** Python 3 (FastAPI endpoint, asyncio), pytest; React + TypeScript (Vite), pure `.mjs` models tested with `node --test`.

**Spec:** `docs/finbot-new-kernel-plan-2026-11-22.zh-CN.md` section 4.5 (in the main checkout, untracked; the binding parts are copied below). Findings that motivate (a): `docs/reports/2026-11-kernel-1b1.md`, section 「没解决的」.

## Global Constraints

- Turns of the old engine look and behave exactly as before on every surface. Everything new is driven by events only the kernel emits (`narration`, `checklist`, `tier`) or by fields only its rows carry.
- The model's only new duty is the optional integer `item`. Nothing blocks when `say` or `item` is missing.
- `say` and `item` never reach a tool. Tool definitions are identical in every model call of a turn; the kernel's own tools stay last, in the order `plan`, `escalate`.
- Stored text = shown text: narration and checklist never enter the answer text.
- Sentences are shown as the model wrote them. No tool identifiers (`query_financials`, `escalate`, `plan`) appear in anything a user sees for a kernel turn.
- User-facing copy is Simplified Chinese; new web strings go through `t()` and get an entry in the English dictionary like their neighbours.
- Python tests: `/Users/wupeng/Monash/monash-ai/projects/market-evidence-agent/.venv-rag/bin/python -m pytest -q -W ignore <files>`. Two tests fail on main for unrelated reasons (`test_sw1_existence_knowledge::test_t39…`, `test_sw1b_sample_aggregate::test_b17…`); leave them.
- Frontend: `cd frontend && npm run test:i18n && npm run build` (the worktree has `node_modules`). A new `scripts/*.test.mjs` file must be added to the `test:i18n` list in `frontend/package.json`.
- Commit after each task with a plain-English message ending in `Co-Authored-By: Claude Fable 5.2 <noreply@anthropic.com>`.

## Review Focus

1. A model that never fills `item` and never calls `plan` again: the checklist must still end fully ticked when the answer arrives, and never show an item ticked while a later labelled item is still open and it was never worked on.
2. A `plan` call and labelled reads in the same step: the list the user sees first already has the labelled item as 进行中, and it is on screen before the reads run.
3. A turn cancelled by the user after two sentences and a checklist: after a page reload the sentences and the checklist are still there.
4. An old-engine turn in Telegram: the progress message reads exactly as today (`收到，正在处理……` then `正在调用：…` lines), including the throttle.
5. A WeChat turn that answers in four seconds sends exactly one message (the answer).

### Task 1: Kernel — the checklist keeps itself, plain and slow-step sentences, a tier event

**Files:**
- Modify: `app/kernel/progress.py`, `app/kernel/toolrun.py`, `app/kernel/loop.py`, `app/kernel/prompt.py`, `app/kernel/tiers.py` (only if needed for the tier event)
- Test: `tests/test_kernel_progress.py`, `tests/test_kernel_toolrun.py`, `tests/test_kernel_tiers.py`

**Interfaces — produces (later tasks rely on these exact shapes):**
- Stream events: `{"event": "narration", "text": str}` with optional `"item": int` (1-based checklist number of the call that carried the sentence) and optional `"system": True` (the kernel wrote it, not the model); `{"event": "checklist", "items": [{"text": str, "status": "pending"|"doing"|"done"|"failed"}]}`; `{"event": "tier", "tier": "mid"|"high"}` once each time the tier actually rises.
- `final_protocol` keeps `{"tier", "narration": [str], "checklist": [...]}`; system sentences are in `narration` too, as plain strings.

**What to build in `progress.py`:**
- `ITEM_DESCRIPTION = "有清单时，写这次调用是为清单的第几项（从 1 数）。没有清单不用填。"`; `with_say(schema)` now adds two optional properties, `say` first then `item` (`{"type": "integer"}`), before the tool's own.
- `take_progress(arguments: dict) -> tuple[str | None, int | None, dict]`: cleaned `say`, `item` (an `int` ≥ 1, `bool` rejected, anything else `None`), and the arguments without either. `take_say` stays as a thin wrapper returning `(say, rest)` if other code uses it; otherwise replace its callers.
- `mark_items(run, numbers: list[int]) -> bool`: numbers outside `1..len(run.checklist)` are ignored; if none is valid nothing changes. Otherwise every item whose status is `doing` and whose number is not among them becomes `done`, and every named item whose status is `pending` or `doing` becomes `doing` (`done` and `failed` are left alone). Returns whether anything changed.
- `close_checklist(run) -> bool`: called when the turn ends with an answer. `last` = the highest number whose status is not `pending` (0 when all are pending). Every `doing` becomes `done`; every `pending` item numbered above `last` becomes `done`; `pending` items below `last` stay `pending` (never worked on, shown unticked); `failed` stays. Returns whether anything changed.
- `TOOL_PHRASES`: a short verb phrase for each name in `loop.READ_TOOLS`, e.g. `query_financials: "查财务数据"`, `query_stock_prices: "查历史行情"`, `query_market_quote: "查最新报价"`, `query_sec_filings: "查 SEC 备案"`, `search_knowledge: "翻资料库"`, `web_research: "上网搜索"`, `search_configured_news: "查新闻"`, `calculate` / `calculate_formula: "算数"`, `query_portfolio: "看持仓"`, `recall_conversations` / `read_past_conversation` / `read_history_citation: "翻之前的对话"`. A test asserts every `READ_TOOLS` name has a phrase.
- `plain_sentence(names: list[str]) -> str | None`: `"正在" + "、".join(first three distinct phrases, in call order) + "。"`; `None` when no name has a phrase (a step of only `plan` / `escalate`).
- `slow_sentence(names: list[str]) -> str | None`: `"、".join(distinct phrases) + "还没回来，还在等。"`; `None` without phrases.
- `step_narration(calls, text)` now returns `(sentence, item, system)`: the first call's `say` with that call's `item`; else the preamble text; else `plain_sentence` of the step's tool names with `system=True`.
- `PLAN_SCHEMA` description becomes: `"复杂任务（已切换到 high 档）开始时，把要做的事列成清单。之后清单要增、删、改时再带着完整清单调用一次；打勾不用你管，调用工具时在 item 里写第几项即可。简单任务不要用。"`

**What to change elsewhere:**
- `prompt.SAY_LINE` ends with: `切换到 high 档后，先用 plan 列出清单，再逐项去做；之后每次调用工具时在 item 里写上这是清单的第几项，勾由系统来打。`
- `loop._tool_step`: emit the narration event with `item` / `system` only when set; append the sentence to `run.narration`.
- `toolrun.run_step_tools`: strip `say` and `item` with `take_progress`; after the kernel's own calls are settled and before the reads start, call `mark_items` with the step's item numbers and emit one `checklist` event if a `plan` call succeeded or `mark_items` changed something (one event per step, never two). When `escalate` raised the tier, emit the `tier` event.
- Slow step: `SLOW_SECONDS = 10` in `toolrun`. If the reads of a step have not all finished after that long, emit one system narration (`slow_sentence` of the reads still out; skip when `None`), append it to `run.narration`, and keep waiting. Once per step. Make the constant patchable so tests use a few milliseconds.
- `loop._finish`: on a successful answer call `close_checklist` and emit a `checklist` event if it changed; do this before the result is built so `final_protocol.checklist` is the closed list. Not on the empty-answer failure.

### Task 3: Web page — sentences above the answer, a live checklist, a folded line afterwards

**Files:**
- Create: `frontend/src/turn-progress.mjs`, `frontend/src/turn-progress.d.mts`, `frontend/scripts/turn-progress.test.mjs`, `frontend/src/app/chat/TurnProgress.tsx`
- Modify: `frontend/package.json` (test list), `frontend/src/api/conversations.ts` (message type; make sure a loaded message keeps `narration`, `checklist`, `tier`), `frontend/src/app/chat/ChatSessionProvider.tsx` (the three events), `frontend/src/app/chat/Message.tsx` and `TurnSteps.tsx` (placement), the English dictionary

**Spec (4.5, binding):** sentences stack, they do not replace each other; the bot's thinking animation stays next to the newest sentence; when the answer is out they fold to one line that can be opened again and survives a reload; the checklist is shown in the conversation with ☑ done, ◐ in progress, ☐ pending, and folds to a count; only kernel turns change.

**Pure model `turn-progress.mjs` (tested with `node --test`):**
- `KERNEL_TOOLS = ["escalate", "plan"]`; `lookups(toolTrace)` = tool-trace entries whose name is not a kernel tool.
- `progressModel({ narration, checklist, tier, toolTrace, running }) -> null | { sentences: string[], current: string | null, items: {text, status}[], doneCount: number, lookupCount: number, tierLabel: "" | "中档" | "高档" }`. `null` when the message has no narration, no checklist and no tier above low (an old-engine message, or a kernel turn that answered directly): the caller then renders exactly what it renders today. While `running`, `current` is the last sentence and `sentences` the ones before it; when not running `current` is `null` and `sentences` is all of them.
- `foldedLine(model, seconds)` → the pieces of the one-line summary, in order and only when non-empty: `已思考 {seconds} 秒`, `查了 {lookupCount} 次`, `清单 {doneCount}/{items.length} 项`, `tierLabel`.

**Session provider:** `narration` appends `event.data.text` to the live message's `narration`; `checklist` replaces `checklist` with `event.data.items`; `tier` sets `tier`. A `tool_start` of a kernel tool is not pushed to the tool list and does not set the 「正在查询研究数据…」 status. While a kernel turn has a sentence, the status text shown in the thinking slot is that sentence.

**Component `TurnProgress`:** rendered where `TurnSteps` is rendered for a message whose `progressModel` is not `null` (and `TurnSteps` keeps rendering for all others, unchanged). Running: earlier sentences as quiet lines; the checklist (if any) as a list with the three marks, the 进行中 item visually current; then the existing thinking slot (animation + newest sentence + seconds). Finished: one button with the folded line; pressing it toggles the sentences and the checklist open in place. Use the tokens and classes the neighbouring components use; no new colours. `data-testid="turn-progress"` with `data-state="running" | "folded" | "open"`.

- Test: the existing Telegram bridge test file that covers `_Progress` (find it with `grep -rl "_Progress\|_progress_text" tests/`)

**Behaviour:**
- `_Progress` keeps `sentences: list[str]` and `checklist: list[dict]` for the turn. A `narration` event appends its text; a `checklist` event replaces the list. The message body is: `ACK_TEXT`, then the checklist one item per line as `☑ 1 text` / `◐ 2 text` / `☐ 3 text` / `☒ 4 text` (done / doing / pending / failed), then the sentences one per line, newest last, keeping the last 6 and the whole body under 3,500 characters (drop the oldest sentences first).

- The throttle stays (`PROGRESS_MIN_INTERVAL`), but an update that arrives inside the interval is not lost: the state is kept and the next edit shows it.
- `finish()`: with a checklist, the final edit is the checklist (as it stands) followed by `DONE_TEXT`; without one, `DONE_TEXT` as today.

### Task 5: WeChat — at most two extra messages, and only for turns that take a while

**Files:**
- Modify: `scripts/run_wechat_bridge.py` (`ask_agent`, the bridge method that calls `self.ask` and replies)
- Test: `tests/test_wechat_bridge*.py` (find with `grep -rl "run_wechat_bridge" tests/`)

**Behaviour (WeChat cannot edit a sent message; every line is a new message):**
- `ask_agent(http, credential, bot_id, text, on_event=None)` parses the stream as it arrives and awaits `on_event(kind, data)` for each event, the same way `scripts/run_telegram_bridge.py` does around its `sse_events(block + "\n\n")` loop; the return value is unchanged.
- Per turn, the bridge sends at most two messages before the answer:
  1. the checklist, the first time a `checklist` event arrives: `我分几步来做：` then `1. text` lines. Sent once; later checklist events send nothing.
  2. one sentence: `PROGRESS_AFTER_SECONDS = 10` after the turn started, if no sentence has been sent yet and the answer has not arrived, send the newest `narration` text seen so far; if none has been seen yet, send the next one when it arrives. Sent once per turn.
- A failure to send a progress message is logged and never stops the turn. The answer is sent as today.
