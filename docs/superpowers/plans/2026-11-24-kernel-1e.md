# Stage 1e Implementation Plan — a channel layer for proactive messages

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Alerts, briefs and notifications reach the owner on WeChat as well as Telegram, a message that cannot be delivered on one channel goes out on the next, and every proactive message has a delivery record that says where it went and whether the owner has been back since.

**Architecture:** Conversations already work over both channels (each bridge is a client of the same endpoint and answers where it was asked). What is Telegram-only is the outbox: `agent_telegram.enqueue` writes rows of `agent_telegram_messages` that only the Telegram bridge sends. This slice makes that outbox channel-neutral: a row names its channel; the owner's preference (which channels, in what order, one or all) decides which rows a message gets; each bridge sends the rows of its own channel; a row that fails or sits unsent is closed and the message is re-queued on the next channel; an inbound message from the owner on a channel acknowledges what was sent there. The two bridges are not rewritten.

**Tech Stack:** Python 3 (SQLAlchemy, asyncio, FastAPI), pytest; one control on the React notifications settings page.

**Spec:** `docs/finbot-new-kernel-plan-2026-11-22.zh-CN.md` section 8 (main checkout, untracked). Binding parts: 「主动消息按紧急程度选通道……每条主动消息有投递记录：已发出、已送达、已确认」; 8.4.1 「提醒发件箱改走通道层，这样微信也能收到提醒」.

## Global Constraints

- **With no preference stored, behaviour is exactly today's:** one row per message, channel `telegram`, the same errors (`telegram_not_bound`, `notify_daily_cap`, `unknown_bot`), the same daily-cap arithmetic, the same Telegram text. Every producer keeps calling `agent_telegram.enqueue` with today's signature.
- **Only the owner is ever messaged.** Telegram: the bound chat (or the bot's own bound Telegram bot), as today. WeChat: `state["owner_user_id"]` of the bridge's login state, nobody else, never a user id taken from a message row.
- **No secret leaves its place.** The WeChat bot token and context tokens stay in the bridge's state file and process; they are never written to the database, logged, returned by an endpoint or put in a message. Delivery records hold text the owner was sent, a channel name, timestamps and short codes.
- A message is delivered **at most once per channel**. A row that was closed (failed or expired) is never sent later, even if its bridge comes back.
- The daily cap counts **messages, not rows**: a message that fans out to two channels, or fails over, counts once.
- Schema changes are additive and idempotent (`ADD COLUMN IF NOT EXISTS`, `create_all`), run at API startup, and tolerate the bridges starting before or after the API.
- Conversation paths of both bridges (inbound message → endpoint → reply) are not changed except for the one acknowledgement call each.
- User-facing copy is Simplified Chinese; new web strings go through `t()` with an English dictionary entry like their neighbours.
- Tests: `/Users/wupeng/Monash/monash-ai/projects/market-evidence-agent/.venv-rag/bin/python -m pytest -q -W ignore <files>`. Two tests fail on main for unrelated reasons (`test_sw1_existence_knowledge::test_t39…`, `test_sw1b_sample_aggregate::test_b17…`); leave them. Do not start a background run of the whole suite. Frontend tests cannot run in this worktree (dangling `node_modules`); CI runs them.
- Commit after each task, plain-English message, files by name.

## Review Focus

1. No preference stored, Telegram bound, WeChat connected: a queued alert makes exactly one row, channel `telegram`, and the Telegram bridge sends it as today. WeChat gets nothing.
2. Preference `["wechat", "telegram"]`, mode `first`: the WeChat send fails three times → one Telegram row appears, once; the WeChat row is `failed` and is never sent afterwards.
3. Same preference, the WeChat bridge is not running: after five minutes the message goes out on Telegram, once; when the WeChat bridge starts an hour later it does not send the expired row.
4. Mode `all`: one message, two rows, both sent, the daily cap decreases by one.
5. The owner sends anything on WeChat: every WeChat row sent before that and not yet acknowledged gets `acked_at`; Telegram rows are untouched.

### Task 1: the channel-neutral outbox

**Files:**
- Create: `app/channels.py`
- Modify: `app/agent_chat_models.py` (columns, one table), `app/agent_telegram.py` (`ensure_columns`, `enqueue`, `sent_today`, `pending_messages`, `mark_sent`, `mark_failed`), the API module that serves Telegram status (find it: `grep -rn "telegram" app/*_api.py | head`), `app/main.py` if `ensure_columns` is not already run at startup
- Test: `tests/test_channels.py` (new); the existing Telegram outbox tests must pass unchanged (`grep -rl "enqueue\|pending_messages\|mark_failed" tests/`)

**Interfaces — produces:**
- `agent_telegram_messages` gains: `channel VARCHAR(16) NOT NULL DEFAULT 'telegram'`; `group_id UUID NULL` (the rows of one message share it; NULL means the row is its own group); `acked_at TIMESTAMPTZ NULL`; `failure VARCHAR(40) NULL` (why a row was closed: `send_failed` | `expired` | `not_connected`).
- New table `agent_channel_prefs`: `owner_hash VARCHAR(64) PRIMARY KEY`, `channels TEXT NOT NULL` (a JSON list), `mode VARCHAR(8) NOT NULL`, `updated_at TIMESTAMPTZ`.
- `app/channels.py`:
  - `CHANNELS = ("telegram", "wechat")`; `MODES = ("first", "all")`; `STUCK_SECONDS = 300`.
  - `prefs(db, owner_hash) -> {"channels": list[str], "mode": str}` — `{"channels": ["telegram"], "mode": "first"}` when nothing is stored. `set_prefs(owner_hash, channels, mode) -> dict` validates (non-empty, each in `CHANNELS`, no duplicates, mode in `MODES`; else `ValueError("invalid_channels")`).
  - `available(db, owner_hash, channel, bot) -> bool` — `telegram`: today's rule (the bot's own bound Telegram bot, or the shared bind). `wechat`: the bridge's login state file exists and has a bot token and an owner user id (`agent_wechat.load_state()`; only its presence is read, nothing is returned from it).
  - `targets(db, owner_hash, bot) -> list[str]` — the channels a new message gets rows on: mode `all`, every available channel in preference order; mode `first`, the first available one.
  - `pending(owner_hash, channel, limit=20, telegram_bot_row_id=None) -> list[dict]` (`id`, `bot_id`, `text`), oldest first. For `telegram` the `telegram_bot_row_id` filter works as `agent_telegram.pending_messages` does today.
  - `mark_sent(message_id, external_id: int | None = None)`; `mark_failed(message_id, code="send_failed")` — one more attempt; at `agent_telegram.SEND_ATTEMPTS` the row is closed (`status="failed"`, `failure=code`) and `fail_over` runs in the same transaction.
  - `fail_over(db, row) -> bool` — when the owner's preference lists another channel that is available and has no row in this message's group, insert one `pending` row there (same `group_id`, `bot_id`, `source`, `inbox_item_id`, text) and return True. Both modes (in `all` every listed channel already has a row, so nothing is added).
  - `expire_stuck(owner_hash, now=None) -> int` — every `pending` row of this owner older than `STUCK_SECONDS` is closed (`failed`, `failure="expired"`) and failed over; returns how many were closed. Safe to call from several processes at once (row locks / `SKIP LOCKED`, no double fail-over).
  - `acknowledge(owner_hash, channel, now=None) -> int` — `sent` rows of that channel with `acked_at IS NULL` get `acked_at = now`.
  - `deliveries(owner_hash, limit=50) -> list[dict]` — newest first: `id`, `group_id`, `bot_id`, `source`, `channel`, `status`, `failure`, `created_at`, `sent_at`, `acked_at`, `text` (first 120 characters). Rows with `source == "reply"` are not proactive messages and are left out.
- `agent_telegram.enqueue(db, owner_hash, bot_id, text, *, source, now=None, inbox_item_id=None) -> int`: same signature, same return, same errors. It asks `channels.targets`; no target → `NotifyError("telegram_not_bound")` (the code name stays for callers); it writes one row per target with a shared `group_id` when there is more than one. A `wechat` row's text keeps the 「【名字】」 prefix (WeChat has one bot for all); a `telegram` row follows today's own-bot rule.
- `agent_telegram.sent_today` counts messages: rows whose `group_id` is NULL plus one per distinct `group_id`.
- `agent_telegram.pending_messages`, `mark_sent`, `mark_failed` keep their signatures and now delegate to `channels` for channel `telegram` (so the Telegram bridge needs no change to keep working, and a Telegram failure fails over).
- Endpoints (owner only, same auth as the Telegram status endpoints): `GET /agent-chat/channels` → `{"prefs": {...}, "available": {"telegram": bool, "wechat": bool}}`; `PUT /agent-chat/channels` with `{"channels": [...], "mode": ...}` → the stored prefs (400 on invalid); `GET /agent-chat/channels/deliveries?limit=` → `{"items": [...]}`.

### Task 2: the bridges deliver, acknowledge and expire

**Files:**
- Modify: `scripts/run_wechat_bridge.py`, `scripts/run_telegram_bridge.py`
- Test: `tests/test_wechat_bridge.py`, the Telegram bridge test file that covers `_deliver_outbox` (find it; create `tests/test_telegram_outbox.py` if none)

**Interfaces — consumes Task 1.**
- WeChat bridge:
  - A delivery pass, run every `OUTBOX_INTERVAL = 5` seconds beside the long poll (its own task; a slow poll must not hold it up): `channels.expire_stuck(owner)`, then for each `channels.pending(owner, "wechat")`: send to `state["owner_user_id"]` with the newest context token the bridge holds for that user (`state["context_tokens"]`), as plain text in `agent_wechat.split_text` chunks; all chunks accepted (`agent_wechat.send_result` says so) → `channels.mark_sent(id)`; otherwise `channels.mark_failed(id, "send_failed")`. With no context token held for the owner the send is still attempted without one (whether such a push arrives is exactly what the owner wants to observe); log `outbox_sent` / `outbox_failed` with the row id and the send result code only.
  - While the login is stale (the bridge is in its pause), no send is attempted and the rows are left to expire.
  - An inbound message from the owner calls `channels.acknowledge(owner, "wechat")` before it is handled.
  - A failure of the delivery pass (database down, an exception in a send) is logged and never stops the bridge or the poll.
- Telegram bridge: each outbox cycle calls `channels.expire_stuck(owner)` before sending; an inbound message or button press from the bound owner calls `channels.acknowledge(owner, "telegram")`. Nothing else changes (`_deliver_outbox` keeps using `tg.pending_messages` / `mark_sent` / `mark_failed`).
